
# Contributing to MarkShark

Thank you for your interest in MarkShark. Contributions of all kinds are welcome, including feedback from instructors and teachers who use the software in real classes.

MarkShark was built to reduce friction in grading paper exams. The goal of this document is to make contributing just as low friction.

⸻

## What counts as a contribution

You do not need to be a software developer to contribute.

Useful contributions include:
	•	Reporting bugs or unexpected behavior
	•	Describing how MarkShark behaves in real teaching workflows
	•	Suggesting improvements to usability or defaults
	•	Contributing bubble sheet templates
	•	Improving documentation or examples
	•	Testing new releases and reporting issues
	•	Small code fixes or larger feature proposals

If it helps instructors grade exams more easily, it belongs here.

⸻

## Before opening an issue

If you encounter a problem, please include:
	•	What you were trying to do
	•	What you expected to happen
	•	What actually happened
	•	Your operating system (Mac, Windows, Linux)
	•	How you installed or ran MarkShark (CLI or GUI)

Screenshots, sample PDFs, or anonymized examples are extremely helpful, but not required.

If you are unsure whether something is a bug or a feature request, open an issue anyway. We can sort it out together.

⸻

## Feature requests

Feature requests are welcome, but MarkShark has a clear design philosophy:
	•	Reduce setup friction
	•	Preserve instructor control
	•	Prefer sensible defaults over complex configuration
	•	Avoid assumptions about centralized IT or institutional workflows

When suggesting a feature, it helps to explain:
	•	The teaching problem you are trying to solve
	•	How you currently work around it
	•	Whether this would be a common or edge case

Requests that increase complexity or setup burden may be deferred, even if technically feasible.

⸻

## Contributing code

If you would like to contribute code:
	•	Small, focused changes are preferred
	•	Please open an issue before starting large refactors or new features
	•	Code should favor clarity over cleverness
	•	Defaults matter more than options

MarkShark is used by educators who may not be programmers. Changes that improve readability, robustness, or usability are valued more than micro-optimizations.

⸻

## Design principles

Contributions should align with these guiding principles:

-	No permission required.  Users should be able to try and use MarkShark without institutional approval.
-	First success should be fast.  A new user should be able to score a small exam quickly using defaults.
-	Instructor control comes first.
Scoring, rescoring, and timing decisions belong to the instructor.
-	Ordinary hardware only
The software should work with scanners and photocopiers instructors already have.
-	Transparent results
Users should be able to inspect and verify scoring decisions.
-	Power is optional
Advanced configuration should never be required for basic use.

If a contribution conflicts with these principles, it may not be accepted, even if technically sound.

⸻

## Tone and expectations

MarkShark is used by educators under time pressure. Discussions should be respectful, practical, and focused on helping people get work done.

There is no expectation of perfection. Questions, partial ideas, and exploratory contributions are welcome.

⸻

## Licensing

By contributing to MarkShark, you agree that your contributions will be licensed under the same open-source license as the project.

⸻

## Final note

MarkShark exists because grading paper exams should not require permission, fees, or delays. Contributions are most valuable when they help preserve that freedom.

Thank you for helping make the project better.
